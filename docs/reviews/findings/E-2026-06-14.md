### CRITICAL-1 | src/ui/editor/EditorToolbar.tsx:176 | "保存并退出"按钮双重调用 handleExit

```ts
// EditorToolbar.tsx:176
onSaveAndExit?.() ?? onExit?.();
```

**问题分析**: `?.()` (optional-call) 返回 `undefined` 当被调用的函数返回 void
时;`??` (nullish-coalescing) 的语义是 "left 是 null/undefined 时取 right" —
所以无论 `onSaveAndExit` 是否被定义,右侧的 `onExit?.()` 都会被求值。整条语句
相当于:

```ts
if (onSaveAndExit) onSaveAndExit();  // undefined 被 ?? 吞掉
onExit?.();                          // 总是执行
```

`EditorPage.tsx:179` 同时把 `onExit` 和 `onSaveAndExit` 绑到同一个 `handleExit`:

```tsx
<EditorToolbar onExit={handleExit} onSaveAndExit={handleExit} />
```

**影响**:
- 点击"保存并退出"按钮时,`handleExit` 被调用两次
- 当 `dirty===true`:第一次调用触发 dirty-exit 确认对话框(用户已经明确选
  择了保存并退出,不应该再被询问) — 这是严重的 UX bug
- `localStorage.removeItem(DRAFT_KEY)` 跑两次
- 任何 `onSaveAndExit` 的副作用都会跑两遍
- E2E 测试不稳定 — 点击后会卡在对话框,后续断言失败

**修复建议**:

```ts
// 方案 1:明确分支(推荐)
if (onSaveAndExit) {
  onSaveAndExit();
} else {
  onExit?.();
}

// 方案 2:把 handleExit 拆成两份真正的不同 handler
// EditorPage.tsx:
//   <EditorToolbar
//     onExit={handleExit}
//     onSaveAndExit={handleSaveAndExit}  // 不需要 dirty-exit 对话框
//   />
```


**问题分析**: `tsc -b --noEmit` 报告 `Button.tsx:45:20 error TS7053: Element

```ts
// 方案 1: 在 ButtonProps 中显式声明 data-testid
export interface ButtonProps extends Omit<ButtonHTMLAttributes<HTMLButtonElement>, 'type'> {
  // ...
  'data-testid'?: string;

// 方案 2: 使用 rest spread
return (
  <button
    {...rest}
    onClick={onClick}
    disabled={disabled}
    className={className}
    style={...}
  >
    {children}
  </button>

```

### MEDIUM-1 | src/store/editorStore.ts:511-526 | placePickup 不检查 exit 单元格

```ts
// editorStore.ts:511-526
placePickup: (x, z) => {
  const { level } = get();
  if (!isFloor(level, x, z)) return;
  // Match the runtime: never let a pickup sit on the start cell.
  if (level.start.x === x && level.start.z === z) return;
  // ❌ 不检查 exit cell!
  const newPickup: Pickup = {
    id: generateId(), x, z, type: 'time', value: 10,
  };
  const nextLevel: MazeData = { ...level, pickups: [...level.pickups, newPickup] };
  set(commitLevel(get(), nextLevel, null));
}
```

**问题分析**: 只挡掉 start cell,没挡掉 exit cell。`validateMaze` 在 save 时
会拒绝 pickup on exit,所以错误信息在"保存"那一刻才出现,而不是点选时就提示。
`placeStart`/`placeExit` 也不挡对向 — 系统性不一致。

**影响**:
- 编辑器 UX 不一致
- 错误信息延后到 save 才出现,用户可能放置了多个 pickup 才发现第一个冲突

**修复建议**:

```ts
placePickup: (x, z) => {
  const { level } = get();
  if (!isFloor(level, x, z)) return;
  // Match the runtime: never let a pickup sit on start or exit.
  if (level.start.x === x && level.start.z === z) return;
  if (level.exit.x === x && level.exit.z === z) return;  // ← 新增
  // ...
}

// 同理:
placeStart: (x, z) => {
  // ... 加 if (level.exit.x === x && level.exit.z === z) return;
}

placeExit: (x, z) => {
  // ... 加 if (level.start.x === x && level.start.z === z) return;
}
```

### MEDIUM-2 | src/maze/JsonMazeProvider.ts:70-78 | size.width/size.depth 没验证为正整数

```ts
// JsonMazeProvider.ts:77-78
const width = requireNumber(size, 'width', `${id}.size`);
const depth = requireNumber(size, 'depth', `${id}.size`);
```

**问题分析**: `requireNumber` 只检查 "is finite number"。手工构造的 JSON
`{size: {width: -5, depth: 10.5}}` 会通过:

- `depth = 10.5`:`m.walls.length !== depth` 会失败,但错误信息是"walls 行数
  不匹配",误导用户
- `width = -5`:下游 `Array.from({length: -5}, ...)` 是空数组,然后 `walls[z]
  ?.[x]` 返回 undefined,`level.start.x` 检查也会出错,但错误链很长

**影响**: 错误信息不友好;攻击面更宽(虽然 `validateMaze` 的下游检查最终
会兜住)。

**修复建议**: 在 requireNumber 后加 integer + positive 检查:

```ts
const width = requireNumber(size, 'width', `${id}.size`);
const depth = requireNumber(size, 'depth', `${id}.size`);
if (!Number.isInteger(width) || width <= 0) {
  throw new LevelLoadError(`Maze '${id}': size.width must be a positive integer`);
}
if (!Number.isInteger(depth) || depth <= 0) {
  throw new LevelLoadError(`Maze '${id}': size.depth must be a positive integer`);
}
```

### MEDIUM-4 | src/maze/importExport.ts:135-137 | sanitizeFilename 允许 `.` 且 `\w` 是 ASCII-only

```ts
// importExport.ts:135-137
export function sanitizeFilename(name: string): string {
  return name.replace(/[^\w-]/g, '_').slice(0, 64);
}
```

**问题分析**:
- `.` 不在排除集(`[^\w-]`),所以 `..` 或 `.hidden` 会原样通过
- `\w` 在非 Unicode flag 下是 ASCII-only(`[A-Za-z0-9_]`),所以中文/日文文
  件名会被完全擦掉成 `_`

**影响**:
- `..` 文件名可能让某些浏览器/下载管理器出现特殊行为
- 中文文件名用户看到的是乱码 `_`(本来应该是 `迷宫_01` 之类)

**修复建议**:

```ts
export function sanitizeFilename(name: string): string {
  // 显式包含 `.`,且去掉 leading dots(防 `..` 路径穿越)
  const safe = name.replace(/[^A-Za-z0-9_.-]/g, '_').slice(0, 64).replace(/^\.+/, '');
  return safe || 'level';
}
```

### LOW-1 | src/maze/AlgorithmMazeProvider.ts:46,56 | logicalSize/2 用 Math.ceil 掩盖了 size 假设

```ts
// AlgorithmMazeProvider.ts:46,56
const logicalSize = Math.ceil(seed.size / 2);
exit: { x: 2 * (logicalSize - 1), z: 2 * (logicalSize - 1) }
```

**问题分析**: 当前 `MAZE_SIZE_VALUES = [15, 30, 50]` 都正常工作,但
`Math.ceil` 掩盖了 "算法生成的 maze 的 exit 必须在 logical cell 上,而
`(size-1)/2 * 2` 必须在 grid 内" 的假设。`Math.ceil(29/2)=15` → `(28,28)`
在 29×29 grid 内 OK;`Math.ceil(30/2)=15` → `(28,28)` 在 30×30 grid 内也
OK 但 reasoning 不清晰。

**影响**: 当前无 bug,但未来加新 size 时容易出错。

**修复建议**:

```ts
// 算法生成的 maze 一定走 odd cells,所以 `(size-1)/2` 是最末 logical cell 索引
// (x2 后是 grid 内最末偶数索引 cell)
const lastLogical = (seed.size - 1) / 2;
// ... exit: { x: 2 * lastLogical, z: 2 * lastLogical }
```
