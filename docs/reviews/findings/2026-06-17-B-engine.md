## §3 HIGH

### H-1 | `src/engine/Scene.ts:191, 195, 212` | 三个 CanvasTexture 在 dispose 后没有被 `null` 引用前就 leak 内存(per-frame texture rebuild 的级联放大)

**观察**: `createFloorTexture()`(L191)、`createWallTexture()`(L195)、`createCloudTexture()`(L212)三个 CanvasTexture 在 `buildScene` 内部被构造并赋值给 material.map,然后 `material.map` 由 `disposeScene` 的 `disposeTex(map)` 通过 `material.dispose()` 触发释放 —— 路径正确。但是,F2 的修复说 "disposeScene disposes every material's .map, which includes hoisted textures, so the GPU still re-uploads on every level transition",而当前 `createXxxTexture` 函数是 per-build 调用(L16-113),意味着每次 `startLevel` 都重新生成三个 CanvasTexture 实例。`disposeScene` 通过 `WeakSet<THREE.Texture>` `disposedTexs` 做了跨调用去重 —— 但 `seenTexs`/`disposedTexs` 用的是 WeakSet,GC 后会失效。如果同一个 `THREE.CanvasTexture` 实例在两帧之间被 GC,`WeakSet` 中的引用消失,后续 `disposeScene` 拿到一个**已 GC 但未被 dispose**的 texture 引用时(React strict-mode double-mount 的典型场景),`dispose()` 静默失败,GPU 端 buffer 不释放。

**为什么这是 HIGH 不是 MEDIUM**:React strict-mode dev 模式下,`GameCanvas` 的 Effect 1 会在 mount/unmount 两次之间快速调用 `dispose()`。如果两次 buildScene 之间 GC 发生,Three.js GPU texture handle 永久 leak。生产环境(prod build 不开 strict-mode)下不会触发,但是 dev 环境下每次导航进出 GameCanvas 都会泄漏;Playwright E2E 也开 strict-mode 一次性的影响下问题更难定位。

**复现路径**:
1. 在 dev 模式下打开游戏进入 GameCanvas
2. React 18 strict-mode 卸载一次再 mount(Effect 1 cleanup → 第二次 effect 跑)
3. 关闭页面前不会 GC(disposeScene 在 effect 内调用)
4. 如果某个 callback 让 dispose 之后才能访问到 texture(例如 future 错误处理路径),dispose 链断裂

**修复建议**:把 `disposedTexs` / `doubleDisposeWarned` 改成 `Set<THREE.Texture>`(强引用)+ 在 `disposeScene` 末尾清理 disposed 项;或者在 `material.dispose()` 之前手动 `material.map = null` 防止 WebGLRenderer 持有引用。Three.js 官方推荐做法:dispose material → texture.dispose() → material.map = null。

参考:`https://threejs.org/docs/#manual/en/introduction/How-to-dispose-of-objects`

### H-2 | `src/engine/Game.ts:304-305` | `new Loop(...)` 紧跟 `loop.start()`,但 `startLevel` 是从 React effect(`useEffect`)中调用的 —— 当 React 在 commit 阶段同步调用 effect 时,`Loop` 闭包内的 `_currentMaze` 在 effect 首次运行后尚未被下一帧读取就被 `dispose()` 清理,造成 rAF callback 第一次 fire 时 `currentMaze` 仍指向旧实例

**观察**: `startLevel` 末尾 L304 `this.loop = new Loop((dt) => this.update(dt));` 然后 L305 `this.loop.start();`。`Loop.start()` 立即 `requestAnimationFrame(tick)`(L20),tick 第一次 fire 时,`update()` 会读取 `this.currentMaze`(L270 同步设置)、`this.player`(L268 同步设置)。在同步路径下顺序正确。

但是有一个 race:**React 18 concurrent mode 下,Effect 2 的 `[maze.id, restartKey]` 依赖可能因为 restartKey 的 setState 让 effect 在 commit 之后异步触发**。如果 Effect 2 的 cleanup(无显式 cleanup,所以不存在)和 Effect 1 的 cleanup 在同一次 React commit 中执行,而 Effect 1 cleanup 调用 `game.dispose()`(L118),那 Effect 2 在后续 commit 才跑 `startLevel`。但 effect 的依赖列表与执行顺序是确定的,R2 的设计是为了避免 dispose/rebuild 路径。

实际上,**真正的 race 在 hot-reload (HMR)**:Vite HMR 重置 `GameCanvas` 模块时,如果新 effect 跑前 React 没调旧 cleanup(L115-120),新 `game.init` 创建新 Game,旧 game 的 rAF 还在飞。新旧两个 Game 共享 `window` 上的 `__game` 引用(在 DEV 模式),开发者控制台看到的可能是旧 Game 实例。

**为什么这是 HIGH**:HMR 是 dev-only,但这是 dev 体验的基础路径,开发者每次保存代码都触发一次。

**修复建议**:`startLevel` 之前检查 `this.loop?.stop()` —— L234 已处理;但 dispose 之后再 startLevel 是不可能的(因为 dispose 不调用 startLevel)。**真正缺失的检查**:`game.dispose()` 时检查 `cancelAnimationFrame` 之外的悬挂 callback(Game.update 不应该有悬挂 callback,但 effect 2 顺序倒置时可能)。

或者在 `gameRef.current = null` 之后的所有 `gameRef.current?.xxx` 引用前,加一道 `gameRef.current?.loop?.stopped` 防御性检查。

更具体的:**当前 Effect 2 的 `[maze.id, restartKey]` 依赖没包含 dispose 信号**。如果 Effect 1 cleanup 在 Effect 2 跑之前发生(React 18 strict-mode 下可能),Effect 2 的 `gameRef.current` 为 null,静默 no-op;但旧 Game 的 rAF 还在跑。这是已知的 React 18 + class-instance 模式陷阱。

### H-3 | `src/engine/InputManager.ts:113-120` | `onKeyDown` 没有 `e.preventDefault()`,导致 WASD 在 canvas focus 时触发浏览器快捷键(P2-11 教学关卡中被反例触发)

**观察**: L116-118 `if (e.code === 'KeyP' && !e.repeat) this.togglePauseListener?.();` 等等触发回调,但**没有 `e.preventDefault()`**。后果:
- `KeyW` 在浏览器(Chrome 113+,Firefox)在某些情况下会触发"关闭窗口"或"快速查找"快捷键 —— 但 `KeyW` 在主流桌面浏览器默认无快捷键,这条不严重
- `Space`(空格)默认滚动页面 —— 但 engine 不监听 Space,无关
- `Digit1` / `Digit2` 在某些 input 模式下触发 IME 切换 —— 不严重
- **真正的问题**:`Tab` 键浏览器默认切换焦点,engine 不监听 Tab,所以无关;但 `F5` / `Ctrl+R` 等 hotkey 在 canvas focus 时仍触发浏览器刷新 —— engine 没拦截,Game 整个状态在 HMR 之外被清空

更严重的:`KeyT` 等字母键如果未来被引入用作某动作(例如 TutorialBanner "next step"),如果不 preventDefault,在 form input focus 时会触发 native autocomplete dropdown 行为。但 engine 只听 `KeyP/Digit1/Digit2/KeyW/KeyA/...`,KeyT 不在监听集合,无影响。

**真正的 HIGH**:L115 `if (e.code === 'KeyP' && !e.repeat) this.togglePauseListener?.();` —— KeyP 触发 pause toggle,但当用户在 Settings overlay 输入框里按 KeyP(例如搜索 settings 文本),也应该触发 pause toggle 吗?目前会触发(`window` 级监听器,跨元素 fire),这是**应该的**(GameCanvas 的 Pause overlay 在 stack 顶部时 InputManager 已 `setPaused(true)` —— 但 `setPaused` 只 clear mouse delta,不阻止 keydown,L26-35)。

**修复建议**:`InputManager` 增加 `if (this.paused) return;` 守卫(L107 已经有 pointerLock 守卫,但没有 paused 守卫),让 overlay 期间的 KeyP 不触发 Game.pauseToggle。

### H-4 | `src/engine/Game.ts:168-172` | `init()` 顺序:`createRenderer` / `createCamera` 都 OK,但 `setFov` 走 `bridge.getInitialFov()` 时若 settingsStore 处于 hydration 中段,可能读到 `NaN`

**观察**: L168 `this.camera.fov = this.bridge.getInitialFov();` —— `getInitialFov` 来自 `GameCanvas:82 useSettingsStore.getState().fov`。如果 `settingsStore` 在 mount 时处于 `loading` 状态且 `fov` 还未 hydrate(虽然 settingsStore 是同步初始化的 Zustand store,不存在 async hydration,但 e2e 测试或未来 SSR 模式可能引入),读到 `NaN`。

`setFov` 在后续被 `settingsStore.subscribe` 触发(L182-191)时会再次调用 `clampFov` —— 但 init 路径直接赋值,绕过 clamp。如果 `useSettingsStore.getState().fov` 是 `undefined`(sanitize 失败后默认值应该是 60,但 settingsStore 类型可能不强制),`camera.fov = undefined` 会让 Three.js 内部 projection matrix 报 NaN。

**修复建议**:`init` 中显式走 `clampFov(this.bridge.getInitialFov())`,而不是直接赋值。这与 `setFov` 路径(L179-192)行为对齐。

## §4 MEDIUM

### M-1 | `src/engine/Scene.ts:289-305` | Pickup mesh 的 `siblings` userData 在 dispose 时不被清空,可能导致外部 reference 持有 mesh 引用

**观察**: L295 `lower.userData = { pickup: p, siblings: [] as THREE.Mesh[] };`,L301 `upper.userData = { pickup: p, siblings: [lower] };`,L302 `lower.userData.siblings = [upper];`。两个 mesh 互相通过 userData.siblings 持有引用。当 `disposeScene` 调用 `scene.traverse((obj) => ... g.dispose(); m.dispose();)`(L362-370),mesh 被 dispose 但 **scene 的 children 数组仍包含它们**(disposeScene 没显式 `scene.remove(mesh)`),直到下次 buildScene 创建新的 scene 替换。

**影响**:旧 scene 的 mesh 仍挂在 scene.children,虽然 GPU 资源已释放,但 JS heap 中保留 mesh + geometry 引用。如果 GameCanvas Effect 1 cleanup 跑 `game.dispose()` 后立即 React unmount,旧 Game 的 scene 实例失去引用、被 GC —— 但如果 React strict-mode 下旧 Game 在 disposal 与新建之间被持有(例如 effect 闭包),短暂时间内 scene.children 完整保留。

**修复建议**:disposeScene 末尾加 `scene.clear()` 或 `while (scene.children.length) scene.remove(scene.children[0])`,与 `dispose` 配对。Three.js 文档明确说 "remove from parent before dispose"。

### M-2 | `src/engine/Game.ts:417-441` | Enemy mesh 与 Enemy 实例的顺序同步在 race window 下不一致

**观察**: L417-423 同步 enemies[i].mesh = enemies[i].position;但 L427-441 的 `contact` 检测循环读取的是 `this.enemies[i].position`,而 mesh 同步的是 `this.sceneRefs.enemies[i].position`(场景端)。两个数组顺序必须严格一致 —— `startLevel` L285-293 构造 enemies,L316-323 Scene 构造 enemy meshes —— 顺序依赖 `injectedMaze.enemies` 的输入顺序。

如果 `maze.enemies` 在 hot-reload 中段被 splice/filter(虽然当前不可变,但未来加入 "enemy killed mid-run" 等功能时),同步就破裂。

**修复建议**:把 enemy state machine 与 mesh 绑成单个对象(`{ state: Enemy, mesh: THREE.Mesh }`),用同一个数组迭代。或者在 `sceneRefs.enemies` 上加 `userData.enemy = stateMachine` 引用,反向查找。

### M-3 | `src/engine/Collision.ts:76-98` | `collidesAt` 对 OOB 返回 `true`,但 `_grid.get` 的 cellSize=0 保护缺失

**观察**: `grid.get(x, z)` 在 `_grid`(Game.ts:28-33)是 closure,`_grid.cellSize` 在每帧 `update()` 设置。如果 maze 异常导致 `cellSize === 0`,`Math.floor((px - r) / 0) = Infinity`,后续 `cx < 0 || cx >= grid.width` 永真,玩家被永久锁死。

`cellSize` 由 `JsonMazeProvider.validateMaze` 校验 ≥ MIN_CELL_SIZE(0.6),但 `AlgorithmMazeProvider` 与编辑器输出未经过同样的校验 —— 如果某个生成器输出 `cellSize: 0`(例如未初始化的 cellSize),玩家卡死。

**修复建议**:`_grid.get` 在 `cellSize === 0` 时返回 1(视为 wall);或 `resolveMove` 入口检查 `grid.cellSize > 0`,否则 throw。

### M-4 | `src/engine/Loop.ts:13` | `dt = Math.min(0.1, ...)` magic number,标签缺失

**观察**: 已有历史 review 5.6 指出此点未修复,但因为不是 HIGH 故保留。补一句:**`Math.min(0.1, ...)` 没有注释说明 0.1s 的来源(spiral-of-death guard 的典型阈值是 100ms),新人阅读时难以理解为何 0.1 是上限**。

**修复建议**:加 `// F-2026-06-17-M-4: clamp dt to 100ms to prevent spiral-of-death after background tabs / long pauses`。命名常量 `MAX_DT_SECONDS = 0.1`。

### M-5 | `src/ui/GameCanvas.tsx:163-181` | `useGameStore.subscribe` 的订阅清理路径不处理 store 在 unmount 后异步触发的回调

**观察**: L163-181 注册 `useGameStore.subscribe((s, prev) => { ... exitPointerLock() ... })`。Effect cleanup L197 调用 `unsubStore()` —— 但 unsubscribe 是同步的,只是取消注册。如果 callback 已经在事件队列中(zustand v4 的 subscribe 是同步通知,无队列),unsub 在 callback 之后跑不会有竞态。

但是有一个**微妙问题**:callback 内 L165 `if (s.screen === 'paused' && prev && prev.screen !== 'paused')` —— 如果 `prev` 是 undefined(zustand 首次订阅),条件不成立,L165 跳过,但 L178 的 terminal screen 检查也用 `s.screen === 'win'`,与 prev 无关 —— 卸载后 React 18 strict-mode 下,第二个 effect 实例的初始 subscribe 触发会看到 `s.screen === 'win'`,调用 `document.exitPointerLock()` —— 但此时 gameRef.current 已经为 null(L119),所以是 no-op,无副作用。

**真正的问题**:`exitPointerLock()` 调用在 effect 内,effect 已被 cleanup,但 callback 仍是闭包的一部分引用着 `gameRef`。无功能影响,但是**未来添加副作用时容易踩坑**。

**修复建议**:在 callback 入口加 `if (!gameRef.current) return;` 守卫;或在 cleanup 内 `gameRef.current = null` 之后再 unsub。当前代码通过 L178 的 `document.pointerLockElement` 检查部分缓解。
