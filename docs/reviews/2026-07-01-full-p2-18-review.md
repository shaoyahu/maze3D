## §2 CRITICAL Findings

### C-1: 闭合门碰撞失效——`_grid.get` 中 `openedDoors` 存门 id 但检查用坐标

**文件**: [`src/engine/Game.ts:65-69`](../src/engine/Game.ts#L65-L69)
**影响**: 玩家可以直接穿过所有闭合门，无需钥匙。门机关系统完全失效。
**复现**: 任何包含门的关卡——玩家走到门所在格子，碰撞检测不阻挡，直接穿过。

**根因分析**:

```ts
// Game.ts:53 — openedDoors 存的是门 id (如 "door-red-1")
let __SCRATCH_openDoors: ReadonlySet<string> = new Set();

// Game.ts:231 — openDoor 添加的是门 id
openDoor(doorId: string): void {
  this.openedDoors.add(doorId);  // e.g. "door-red-1"
  ...
}

// Game.ts:65-69 — 碰撞检查用 "x,z" 坐标字符串
get: (x, z) => (
  __SCRATCH_currentMaze?.walls[z]?.[x] === 1
  || __SCRATCH_openDoors.has(`${x},${z}`)  // "2,3" — 永远不匹配 "door-red-1"
    ? 1 : 0
),
```

`openedDoors` Set 中存储的是门 id（字符串如 `"door-red-1"`），而 `_grid.get` 用 `has(\`${x},${z}\`)` 检查坐标字符串（如 `"2,3"`）。两者永远不匹配，OR 条件永远为 false，闭合门不会被当作墙处理。

**修复**: 将 `openedDoors` 改为存储坐标字符串 `"x,z"` 而非门 id，或在 `_grid.get` 中遍历 `maze.doors` 检查门的坐标是否在 `openedDoors` 中。推荐方案 A（最小改动）:

```ts
// openDoor 改为存坐标
openDoor(doorId: string): void {
  const door = this.currentMaze?.doors.find(d => d.id === doorId);
  if (door) this.openedDoors.add(`${door.x},${door.z}`);
  const mesh = this.sceneRefs?.doors.get(doorId);
  if (mesh) mesh.visible = false;
}

// startLevel 重置保持不变
this.openedDoors = new Set<string>();
```

或者方案 B（更清晰，但改动更大）: 维护一个 `closedDoorCells: Set<string>` 存所有**未开**门的坐标，`openDoor` 时从 set 中 remove。`_grid.get` 检查 `closedDoorCells.has(\`${x},${z}\`)`。

## §3 HIGH Findings

### H-1: `findAdjacentDoorForUnlock` 函数名和注释声称检查邻接，但实现不检查

**文件**: [`src/game/Rules.ts:111-123`](../src/game/Rules.ts#L111-L123)
**影响**: 玩家在关卡任何位置使用钥匙，可以打开关卡中任意同色门（包括远处的门）。降低了谜题难度，违背了"4-邻接"的设计意图。
**复现**: 玩家在 (0,0) 拿到红钥匙，走到 (5,5) 按下使用键——即使 (1,2) 的红门不与玩家邻接，也会被打开。

**注释说**:
```ts
// P2-18: find a closed door adjacent to the player's current cell that
// matches the given key color. "Adjacent" = 4-neighbour (Manhattan distance 1).
```

**但实现**:
```ts
function findAdjacentDoorForUnlock(
  keyColor: KeyColor,
  maze: MazeData,
  openedDoorIds?: ReadonlySet<string>,
): string | null {
  const openSet = openedDoorIds ?? new Set<string>();
  for (const door of maze.doors) {
    if (door.keyColor !== keyColor) continue;
    if (openSet.has(door.id)) continue;
    return door.id;  // ← 直接返回第一个匹配门，无邻接检查
  }
  return null;
}
```

**修复**: 函数签名需加入玩家位置参数，遍历 4-邻居方向检查是否有匹配门：

```ts
function findAdjacentDoorForUnlock(
  keyColor: KeyColor,
  playerX: number,
  playerZ: number,
  maze: MazeData,
  openedDoorIds?: ReadonlySet<string>,
): string | null {
  const openSet = openedDoorIds ?? new Set<string>();
  const dirs = [[1,0],[-1,0],[0,1],[0,-1]];
  for (const [dx, dz] of dirs) {
    const nx = playerX + dx;
    const nz = playerZ + dz;
    const door = maze.doors.find(d => d.x === nx && d.z === nz && d.keyColor === keyColor);
    if (door && !openSet.has(door.id)) return door.id;
  }
  return null;
}
```

同步修改 `onUseItem` 调用处传入玩家坐标。

## §4 MEDIUM Findings

### M-1: `onDoorUnlocked` bridge 回调是死代码

**文件**: [`src/ui/GameCanvas.tsx:122`](../src/ui/GameCanvas.tsx#L122)
**影响**: 死代码，不造成功能问题但增加维护困惑。

`GameBridge` 接口声明了 `onDoorUnlocked(doorId)` 回调，`GameCanvas` 实现为 `game.openDoor(doorId)`。但实际门解锁走的是另一条路径：`gameStore.useItem` 把 `unlockedDoorId` 存到 `lastUnlockedDoorId`，然后 `onUseItem` bridge 回调读取它并调 `game.openDoor(id)`。`onDoorUnlocked` 从未被调用。

**修复**: 删除 `GameBridge.onDoorUnlocked` 声明和 `GameCanvas` 中的实现，或在 `gameStore.useItem` 中改用 `onDoorUnlocked` 路径（删除 `lastUnlockedDoorId` 间接传递）。

### M-2: `disposeScene` 不清理 `doors` Map

**文件**: [`src/engine/Scene.ts:399-404`](../src/engine/Scene.ts#L399-L404)
**影响**: `SceneRefs.doors` Map 在 `disposeScene` 后仍持有对已 dispose mesh 的引用。不影响 GPU 资源释放（`scene.traverse` walk 会释放 mesh 的 geometry/material），但下次 `buildScene` 前 `doors` Map 的旧条目可能被误读。

`disposeScene` 签名只接受 `traps: THREE.Mesh[]`，不接受 `doors: Map<string, THREE.Mesh>`。且 `Game.ts` 调用 `disposeScene` 时也不传 `doors`。

**修复**: 要么给 `disposeScene` 加 `doors` 参数并在内部 `doors.clear()`，要么在 `Game.ts` 调用 `disposeScene` 后手动 `this.sceneRefs.doors.clear()`。

### M-3: `Scene.ts` 中 fire/water trap 共享 geometry 但 door 不共享

**文件**: [`src/engine/Scene.ts:344-394`](../src/engine/Scene.ts#L344-L394)
**影响**: 轻微性能浪费。每扇门创建独立的 `MeshLambertMaterial`（因为需要按 keyColor 着色），这是合理的。但 fire/water trap 分别创建了独立 geometry（`PlaneGeometry` 和 `CircleGeometry`），可以被 hoisted 到循环外与 wallGeom/pickupGeom 同级共享。影响极小（几十扇门关卡），标记为信息性。

## §5 LOW Findings

### L-1: trap 碰撞检测每帧触发但依赖 store 侧 0.5s 窗口降频

**文件**: [`src/engine/Game.ts:670-701`](../src/engine/Game.ts#L670-L701)
**影响**: `findTrapAt` 每帧调用。fire trap 伤害通过 `gameStore.damage` 的 invulnerable 窗口合并，water trap 的 `setSlowUntil` 是幂等操作（只是重设时间戳），所以功能上没问题。但每帧调用 `findTrapAt` 并触发 bridge 回调有轻微的无效开销。

**建议**: 在 Game 侧维护一个 `lastTrapHitAt` 时间戳，0.5s 内不重复触发 bridge 回调，类似 `lastDamageAt` 对羊皮纸的保护模式。

## §8 跨切关注

1. **碰撞数据模型不一致**: `_grid.get` 使用坐标字符串 `"x,z"` 做 key，但 `openedDoors` 存门 id。这反映了"运行时状态 (openedDoors) 和碰撞查询 (坐标) 使用了不同的 key space"的设计疏漏。修复 C-1 时应统一 key space。

2. **Bridge 路径冗余**: 门解锁存在两条路径（`lastUnlockedDoorId` 间接传递 vs `onDoorUnlocked` 直接回调），当前只有前者被使用。建议在修复 H-1 时统一为一条路径。

3. **"Adjacent"语义缺失**: `findAdjacentDoorForUnlock` 的"邻接"只在注释和函数名中体现，实现完全忽略。这可能是因为初始实现时玩家位置不可用于 `Rules.ts` 纯函数，但 spec 明确要求 4-邻接。需要重构 `onUseItem` 签名以传入玩家坐标。
